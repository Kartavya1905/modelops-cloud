# Résumé bullets

Every number below comes from the [benchmark report](benchmarks/report.md) and the raw files of the three full benchmark runs it lists (`benchmarks/results/2026-11-11T1023`, `…T1715`, `…T1745`), or the back-to-back A/B runs (`…T1734`, `…T1740`), or from a milestone doc that shows the test that produced it. Ranges cover all three runs; nothing is the best run alone. Pick three or four; keep the links handy for an interview.

**ModelOps Cloud**: a self-service MLOps platform (TypeScript, NestJS, Next.js, Python, PostgreSQL, Redis, Docker, Kubernetes, Terraform), built solo, running on a laptop at zero cost.

- Built a deployment engine that turns a validated ONNX model into an isolated, resource-limited model server behind an authenticated inference gateway, with a durable request path (transactional outbox, idempotency keys, compare-and-set state machine) and a self-healing reconciler. Across three benchmark runs at 50 req/s, **no request failed**, and the gateway (API keys, rate limits, input validation, routing) added **1.5–3.5 ms at the median** over calling the model server directly ([report](benchmarks/report.md#every-full-run-in-the-repository)).
- Implemented canary releases with automatic analysis and one-click rollback: a 10 % canary received **9.9–10.6 % of 6,001 requests** in each run, and rolling back to the previous revision took **54–114 ms (median of 10, per run)** from the API call to the gateway serving it ([report](benchmarks/report.md#every-full-run-in-the-repository)).
- Load-tested the serving path to its limit and found a real design flaw: under overload the reconciler mistook a saturated model server for a dead one and restarted it. I changed the rule (a running server must fail 3 health checks in a row), added a test for it on Docker and Kubernetes, and re-ran the same overload back to back: **restarts 2 → 0, 12.3 % more requests answered** ([report](benchmarks/report.md#the-finding-fixed-old-and-new-restart-rule-ramped-back-to-back), [M12](milestones/m12-benchmarks-demo.md)).
- Made the same orchestration run on Docker and on Kubernetes behind one driver interface; on kind each model is a hardened pod with a NetworkPolicy, and the same lifecycle test suite passes on both, including probes that prove a model server can reach object storage but not the database ([M10](milestones/m10-kind-observability.md)).
- Hardened it against real failures and attacks: a chaos suite (killed worker, flushed Redis, paused Postgres, killed model server) that found and fixed a bug where a database pause failed in-flight deployments; every security requirement in the threat model has an automated test; a hash-chained audit log detects edits even by the database owner ([M9](milestones/m9-reliability-security.md)).
- Set up supply-chain-hardened CI/CD (actions pinned by commit SHA, images by digest, Dependabot with a 7-day cooldown, Trivy scans, SBOM and provenance on published images) and wrote the AWS deployment as Terraform with least-privilege IAM and GitHub OIDC, policy-checked in CI and never applied, with a written cost estimate ([M11](milestones/m11-cicd-terraform.md)).

Measured on one laptop running the whole stack; latency tails varied a lot between runs (the report shows why). Quote medians and ranges, not single best values.
