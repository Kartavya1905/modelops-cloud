**Highest sustained step: 200 req/s** on one model server limited to 0.5 CPU. Each further model server (or a larger CPU limit per revision) adds capacity; the gateway itself has 1 CPU.

What the gateway answered over the whole ramp, all five steps together ([ramp-codes.json](../../benchmarks/results/2026-11-11T1745/ramp-codes.json), Prometheus; `increase()` over the window, so approximate):

| Status | Requests | Meaning |
|---|---|---|
| 200 | 32907 | answered |
| 503 | 6692 | refused at once (circuit breaker open, or no ready revision) |
| 504 | 7137 | the model server did not answer within the 2 s upstream timeout |

Past saturation the model server's queue grows until requests reach the gateway's 2-second upstream timeout (hence p95 values of about 2 000 ms), and the gateway answers with an error instead of waiting longer: overload stays bounded and visible to the client rather than turning into unbounded latency.

### The finding, fixed: old and new restart rule, ramped back to back

The fix (M12): the reconciler takes a **running** model server out of routing and restarts it only after `MO_UNHEALTHY_STREAK` failed health checks in a row (default 3); a crashed or missing one is restarted at once, as before. To compare fairly, the same ramp ran twice in a row on the same machine, first with `MO_UNHEALTHY_STREAK=1` (the old behaviour: one failed check restarts) and then with the default.
